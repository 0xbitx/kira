What it is

A full offensive workbench, built around the request.

Kira sits between your browser and the target as a local HTTPS proxy. Trust Kira's CA once, and every request and response is decrypted, captured and streamed into a native desktop window. Headers, bodies, status codes, timings, TLS details, cookies, query parameters and WebSocket frames are all available for inspection.

From there the workbench takes over. Pause traffic with Intercept, replay and edit it in Repeater, fuzz it with Intruder, run 54 vulnerability checks and 32 recon modules, map the application, capture OAST callbacks and document findings in Notes. Projects keep each engagement separate, on disk or in memory.

Everything after the intercept.

01

Capture & inspector

Live flows stream in over Server-Sent Events. Search, filter by method, status or resource type, pause and follow live, then open any request for headers, bodies, timings, TLS details, cookies, query parameters and WebSocket frames. Copy as cURL or export the capture as HAR 1.2.

Intercept

Arm the queue and new proxied requests pause before they are forwarded. Continue, drop or edit them one at a time or in bulk. Replayed requests from the other tools bypass the queue.

Repeater

Independent tabs with side-by-side request and response editing, redirect following, diffing, per-tab history, shared variables, rewrite rules and repeat/timing runs. Raw HTTP mode sends byte-exact requests for duplicate headers, HTTP/1.0, pipelining and request-smuggling probes.

Install

One binary. One terminal.

No installer, no package manager, no runtime. Download, make it executable, run.

  1. 01

    Get the binary

    Download the Linux x86-64 release, or copy the curl command. The ELF carries the proxy, dashboard, scanner and recon engines.

  2. 02

    Install the desktop stack

    GTK 3 and WebKitGTK 4.1 are the only system libraries. Install them for your distribution:

    Debian / Ubuntu / Kali sudo apt install libgtk-3-0 gir1.2-webkit2-4.1

    Fedora sudo dnf install gtk3 webkit2gtk4.1

    Arch Linux sudo pacman -S gtk3 webkit2gtk-4.1

  3. 03

    Launch Kira

    Run ./kira. The dashboard opens at 127.0.0.1:8787 and the proxy listens on 127.0.0.1:8080.

  4. 04

    Trust the CA

    Download Kira's CA from the dashboard footer or /api/cert, then trust it in your browser. HTTPS is decrypted locally.

No runtime required. Kira does not need Python, Node.js, a proxy framework or a package manager on the target machine. GTK 3 and WebKitGTK 4.1 are the only external dependencies.

Beginner's guide

From your URL to a confirmed finding.

A complete first test in ten small steps. Each step says what to click, what you should see, and what to do if it does not work. The screenshots show the real Kira window.

You need

A site you own

Your own site, a staging copy, or written permission. Never test a site you do not control.

Time

20–30 minutes

One page, one parameter, one confirmed issue. A small finished test beats a huge unfinished scan.

You will produce

One clear finding

A repeatable request, a harmless proof, the impact, and a fix the developer can apply.

!
Test only what you own.

Use a site you own or have written permission to test. For a live business site, use a staging copy and a test account. Testing someone else's website without permission is illegal in most countries, and an aggressive scan can change or delete real data. Stay on your own domain; do not scan third-party services or shared infrastructure you do not control.

Step 0 · pick your target

Write the exact URL down
URL https://your-site.example/search?q=test Owned or authorized

Use one page that takes input. The part after ? is a parameter, and Kira's injection checks test parameters. A search page or product page is a better first target than a plain homepage. If you only have a homepage, add a harmless test parameter such as ?q=test.

Good first targets
  • A search page: /search?q=test
  • A product page: /product?id=1
  • A login or contact form
  • A staging copy with test data
Avoid on the first run
  • Checkout and payment pages
  • Delete, logout or password-change actions
  • Admin actions that change state
  • Third-party services you do not control
  1. 01

    Launch Kira and open a project

    Project picker
    1 min

    Goal: give this test its own project so every request is saved.

    Do this

    1. Run ./kira in a terminal. The dashboard opens at 127.0.0.1:8787; the proxy listens on 127.0.0.1:8080.
    2. Type a project name such as my-site-2026-11 and click Create project. Use Start temporary only if you do not want anything written to disk.
    3. Keep the project open. Kira does not record traffic until a project is open.

    You should see An empty Proxy view, a green LIVE dot, and the project name in the header.

    If it does not work: the dashboard may pick the next free port; use the URL printed in the terminal. If the window does not open, run Kira from a terminal and read the error.

    Tip: use one project per site and date. Captures, notes and findings stay together.

  2. 02

    Put your browser behind Kira

    Proxy → Open browser
    2 min

    Goal: make your browser send traffic through Kira so it can be read.

    Do this

    1. Open the Proxy workspace and click Open browser. Pick an installed Chromium-family browser or Firefox. Kira starts a temporary profile with the proxy and certificate configured.
    2. Prefer your normal browser? Set both the HTTP and HTTPS proxy to 127.0.0.1:8080. Download the CA from the dashboard footer or http://127.0.0.1:8787/api/cert, then trust it.
    3. Disable QUIC/HTTP3 so pages cannot bypass the proxy. In Chrome, set chrome://flags/#enable-quic to Disabled and restart the browser.
    4. Open https://example.com as a quick test.
    Your browsertemporary profile or manual proxy

    Kira proxy127.0.0.1:8080 · decrypted locally

    You should see The page loads normally and a request appears in Kira's traffic list.

    If it does not work: a certificate warning means the CA is not trusted. A page that loads but never appears means the proxy is not set or QUIC is still on. Certificate-pinned apps will not show up.

    Keep it local: the CA private key stays on your machine. Do not share it or install it on a machine you do not own.

  3. 03

    Visit your site and capture the request

    Proxy → traffic list
    3 min

    Goal: record the pages and actions you are allowed to test.

    Do this

    1. Open your target URL in the proxied browser and log in with the test account.
    2. Use the site normally: open the main pages, submit a search, fill in a form. Each action becomes a row.
    3. Pick one request that carries input: a query parameter (?q=test, ?id=1) or a form field. This is your test request.
    4. Click the row to inspect the request and response on the right: method, URL, headers, cookies, body, status and timing.

    You should see Rows with method, host, path, status and size. Authenticated requests show a Cookie header.

    If it does not work: clear the filter, turn Follow live back on, check that the proxy is still running, and refresh the page.

    Tip: the scanner can reuse the cookies from a captured request, so log in before you scan.

  4. 04

    Open the scanner on the same request

    Scan
    1 min

    Goal: point the scanner at the page and session you just captured.

    Do this

    1. Right-click the request and choose Scan request, or open Scan and paste the URL.
    2. Check Target URL. If you opened the scanner from a request, the URL and cookies are already filled in.
    3. Leave Jobs at 1 for the first run and Timeout at 10s.
    4. Leave Tor routing off unless you specifically need it. Scans go directly to the target, not through the proxy.

    You should see The target URL, optional cookies, timeout, jobs, preset buttons and the check list.

    If it does not work: the URL needs http:// or https://. For a local app, use http://127.0.0.1:3000 and make sure it is running.

    Keep it small: a scan sends real requests to the target. Watch rate limits and never point it at shared infrastructure.

  5. 05

    Run a safe first pass

    Scan → Core preset
    2–5 min

    Goal: get a first report without flooding the site.

    Do this

    1. Click Core. It selects cheap, high-signal checks: security headers, CORS, open redirect, sensitive files, XSS, SQLi and a few safe probes.
    2. Read the selected count. For a first run, 10–20 checks is plenty.
    3. Press Run scan and watch the status line. Do not close the window.
    4. If the site slows down, press Cancel, lower Jobs to 1, and run a smaller preset.

    You should see Checks move from pending to done, and findings appear grouped by check.

    Which preset? Start with Core. Add one preset at a time instead of selecting everything.

    Core
    First pass: headers, CORS, redirects, files, XSS and SQLi.
    Web
    Application checks for normal pages and forms.
    API
    JSON endpoints and API-shaped requests.
    SQLi
    More database payloads when SQLi is plausible.
    CMS
    WordPress, Joomla and Drupal specifics.
    WAF
    Detect a firewall or filtering layer.
    Tech
    Fingerprint the server and framework.
    Recon
    Map visible pages and paths.
    All
    Staging only. Slow and noisy; not for a first run.

    If it does not work: a skipped check means a tool is missing or the check does not apply. It is not a failure. A scan that finds nothing is not proof of safety.

  6. 06

    Read the report without panicking

    Scan → results
    5 min

    Goal: separate real issues from noise and pick one candidate.

    Do this

    1. Filter to Critical and High first.
    2. Click a finding and read its message and evidence: a header, a reflected value, an error, or a timing difference.
    3. Treat skipped as “not tested”, not “safe”. Treat Info as context, not a vulnerability.
    4. Pick one candidate and write down the URL, parameter, check name and evidence.
    5. Do not report it yet. You will confirm it by hand in the next step.

    If it does not work: no findings? Try a URL with a parameter, log in first, use the Web or API preset, or map the site to find more pages. A quiet scan is not a clean bill of health.

    False positive: a warning that does not reproduce when you test it by hand. Do not report it as a bug.

  7. 07

    Confirm the finding by hand in Repeater

    Right-click → Send to Repeater
    5 min

    Goal: turn a scanner warning into a proven bug.

    Do this

    1. Right-click the original request and choose Send to Repeater.
    2. Find the parameter named in the finding. Change only that value.
    3. Use a harmless marker first: <b>proof</b> for reflected HTML, a single quote ' for a database error, or https://example.com for an open redirect.
    4. Press Send and compare the response with the original.
    5. Send it two or three times. A real bug behaves the same way each time.

    You should see The marker appears unencoded, a database error appears, or the response redirects. The same result every time.

    If it does not work: the warning may be a false positive. Check the cookie, the parameter name, the encoding and the request method. Try the payload with URL encoding.

    Stop at proof: one bold marker, one error, one redirect. Do not dump tables, read other users' data, or change records.

  8. 08

    Turn it into a harmless proof of concept

    Exploit → PoC / Intruder
    5–10 min

    Goal: produce repeatable evidence you can show to a developer.

    Do this

    1. Open Exploit → PoC in Repeater. It builds a runnable card and curl command for XSS, SQLi, CORS, CSRF, clickjacking, SSRF or XXE.
    2. For blind bugs, open OAST and use the callback URL. A hit proves the target contacted you.
    3. To try several values, right-click the request → Send to Intruder. Mark the value with §, load a small payload list, and keep threads at 1.
    4. Save the exact request, the response and a screenshot.

    You should see A PoC card, a curl command, a callback hit, or a clear response difference.

    If it does not work: check the encoding, the parameter name and the session cookie. Slow down and use fewer payloads.

    Stop at proof: one alert, one error, one callback or one redirect is enough. Do not exfiltrate data, upload a shell, or delete or change records.

  9. 09

    Fix it, then re-test the same request

    Repeater + Comparator
    varies

    Goal: confirm the fix actually closes the issue.

    Do this

    1. Send the developer the URL, parameter, exact request, response evidence, impact and the recommended root-cause fix.
    2. Ask for the root-cause fix: parameterized queries, output encoding, redirect allow-lists, access checks or safer headers.
    3. After the fix, send the exact same Repeater request and run the same scanner check.
    4. Compare the before and after responses in Comparator.

    You should see The old payload now fails or is neutralized, while normal site behavior still works.

    If it does not work: the fix may be partial. Re-test variants and encodings. Do not publish the finding as fixed until the old proof fails.

    If it is Critical: stop testing and tell the site owner immediately.

  10. 10

    Write it down and export the report

    Findings / Notes
    5 min

    Goal: leave one clear finding a developer can reproduce.

    Do this

    1. In Repeater, open Exploit → Findings. Add a title, severity and short notes, then press Capture current.
    2. Use Copy Markdown or Export HTML.
    3. In Notes, keep a short timeline and the fix status.
    4. Include the summary, URL, parameter, steps to reproduce, request/response, impact, fix and evidence.

    You should see One finding a developer can reproduce without asking you questions.

Plain English

The words on screen

Target URL
The exact page you are testing, including the ?parameter=value part.
Parameter
An input the site accepts, such as ?id=1 or a form field.
Scope
The domains and pages you are allowed to test. Stay inside it.
Proxy
A local middleman that records requests between your browser and the site.
Request / response
What your browser sends, and what the site sends back.
Payload
A small test input used to see how the site handles unexpected data.
Encoding
How special characters are written in a URL or HTML. Wrong encoding can hide a real bug.
False positive
A warning that does not reproduce when you test it by hand.
PoC
Proof of concept: the smallest repeatable evidence that a bug is real.
OAST
An outside callback that proves a blind bug made the target contact you.
XSS / SQLi
Script injection in a page / database injection through an input.
CSRF / CORS
A forged action from another site / a rule for which sites may read a response.
SSRF / IDOR
Making the server fetch a URL / reading another user's object by changing an ID.
Severity
An estimate of impact, not a guarantee. Confirm before reporting.

Five rules

Stay safe and legal

  1. Permission first. Own the site or carry written authorization.
  2. Use staging. Prefer a copy and a test account over live customer data.
  3. Read-only first. Avoid delete, payment and password-change actions.
  4. Keep the load low. Jobs at 1, short runs, and watch rate limits.
  5. Stop at proof. Report the issue; do not keep escalating.

Try a better target

Reading results

What the severity labels mean

Kira ranks each finding by likely impact. Start at the top and confirm the issue by hand before you report it.

Critical

Immediate danger: remote code execution, authentication bypass, exposed admin access or live secrets. Fix before anything else.

High

Serious: SQL injection, cross-site scripting with real impact, broken access control or exposed sensitive files. Can lead to data or account compromise.

Medium

Real but conditional: reflected XSS, CSRF gaps, open redirect or weak CORS. Usually needs a user or a specific setup.

Low

Hardening: cookie flags, missing headers, verbose errors or directory listing. Fix after the higher risks.

Info

Context, not a vulnerability: technology versions, DNS, TLS details. Useful for planning, not a finding by itself.

Before you call it done

  • Permission. I used a site I own or have written permission to test.
  • Capture. I recorded the request through Kira.
  • Confirm. I reproduced the issue by hand in Repeater.
  • Proof. I have a harmless PoC that works every time.
  • Report. I wrote the impact and the recommended fix.
  • Re-test. I confirmed the old proof fails after the fix.

One complete result

You do not need to find everything on the first run.

Pick one page, one parameter and one confirmed issue. Fix it, re-test it, and write it down. That is a successful security test, and a much better outcome than a long list of unverified scanner warnings.

Local by design

Your traffic stays on your machine.

Projects, captures, bodies, notes, command logs and settings live on disk or in the browser under your control. There is no account, no telemetry and no cloud backend. The proxy and dashboard bind to loopback by default, and the dashboard uses a strict same-origin CSP.

The AI analyst is opt-in. Context is only sent to the provider you configure when you ask a question. Third-party recon checks such as Shodan, HIBP and URLhaus send target data to those services; default-credential checks, nmap OS fingerprinting and Cloudflare origin probes are explicitly opt-in.

Default guardrails: 5,000 flows in memory, 512 KiB body preview per message and 8 MiB maximum inspected body. Truncation and eviction are shown in the UI.

No cloud

No hosted service, no account and no telemetry. Nothing is hidden behind a subscription.

Loopback by default

Opt-in AI

Text, not HTML

Captured values are rendered as text, and the dashboard stays same-origin under a strict CSP.
